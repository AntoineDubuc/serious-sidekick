Brainstorm with AI Personas

/serious-conversation

Think of this as a roundtable discussion. You describe a topic, and Claude creates a panel of fictional experts — an architect, a skeptic, a user advocate, etc. — who each give their perspective. You read their ideas, respond, and they refine. It's brainstorming, but structured.

When to use it

  • You have a vague idea and want to explore it
  • You want to see different perspectives before deciding
  • You're stuck and need creative input
  • You want to think through trade-offs

What you get

  • Multiple expert viewpoints per round
  • A synthesis that merges the best ideas
  • Versioned artifacts saved to your project
  • A record you can hand off to other skills
How to use it
What you type
> /serious-conversation
1

Claude asks: "What do you want to explore?"

Describe your idea in plain language. It doesn't need to be polished. Example: "I want to add push notifications to my app but I'm not sure how."

2

Claude picks personas and they each weigh in

You'll see responses from several AI "experts" — each with a different angle. The Architect thinks about structure, the Skeptic pokes holes, the Pragmatist focuses on what's practical.

3

You respond and they refine

Tell them what resonated, what you disagree with, or ask a follow-up. They'll adjust and go another round. You do as many rounds as you need.

4

When you're satisfied, the conversation is saved

Everything gets saved to Research/conversations/ in your project. You can reference it later or feed it into /serious-research or /serious-plan.

Example scenario

You: "I need a way for users to share their workout data with a coach. Should it be real-time or just a daily summary?"

Architect: "Real-time has infrastructure costs. Start with batched summaries."

User Advocate: "Coaches want to intervene mid-workout. Real-time matters."

Pragmatist: "Ship daily summaries now, add real-time as a premium feature later."

You: "I like the phased approach. Let's go with that."

Investigate Before You Build

/serious-research

Before writing any code, you need to understand the problem. This skill does structured investigation — it reads your codebase, finds the relevant files, traces how things connect, and writes up findings with evidence. Think of it as hiring a detective for your codebase.

When to use it

  • A bug you can't figure out
  • You want to add a feature but don't know what it would touch
  • You need to understand how something works before changing it
  • You want documented findings, not just a chat answer

What you get

  • A research.md file with structured findings
  • Root cause analysis (for bugs)
  • List of affected files and components
  • Recommended fix or approach
How to use it
What you type
> /serious-research
1

Claude asks what to investigate

Describe the problem or question. Example: "Users are getting logged out randomly after about 30 minutes."

2

Claude asks: quick or deep?

Quick (5-10 min): Claude investigates on its own, then has AI personas review the findings.
Deep (15-30 min): Multiple AI agents investigate in parallel, grade evidence, and do adversarial verification. Use for complex or critical issues.

3

Claude reads your code and investigates

It searches through your project files, traces function calls, reads configuration, and pieces together what's happening. You can watch it work or go grab a coffee.

4

You get a research report

A complete research.md file is saved to Research/bugs/, Research/features/, or Research/exploratory/ depending on what it was. This file feeds directly into /serious-plan.

What the output looks like

Research/
  bugs/
    random-logout/
      research.md ← the main report
      evidence/ ← supporting files
💡
When in doubt, use quick mode. It's fast and covers most cases. Save deep mode for bugs you've already spent hours on, or for changes that touch many parts of your app.

Visualize Before Planning

/serious-mock-ups

Before writing a detailed plan, it helps to see what you're building. This skill generates UI wireframes and visual mock-ups from your research, so you can agree on what the screens look like before anyone writes code. It creates a component inventory and design decisions that feed directly into /serious-plan.

When to use it

  • You're building a new screen or UI feature
  • You want to agree on the look before coding
  • You need to communicate a design to someone
  • You want mock-ups to guide your plan

What you get

  • Wireframe or visual mock-ups
  • Component inventory (list of UI pieces)
  • Design decision log
  • Screen flow diagram
How to use it
What you type
> /serious-mock-ups
1

Claude finds your research

If you ran /serious-research first, Claude picks up where you left off. Otherwise, describe what you want to mock up.

2

Choose a fidelity level

Wireframe: Simple boxes and lines. Visual: Styled with colors and spacing. Interactive flow: Shows how screens connect to each other.

3

Review and iterate

Claude shows you mock-ups. You give feedback ("make the button bigger", "add a search bar"). It revises. Each version is saved with a version number.

4

Output feeds into planning

The component list and design decisions are picked up automatically by /serious-plan, so your plan matches what you approved visually.

💡
This step is optional. If you're fixing a bug or building something with no UI, skip straight to /serious-plan. Mock-ups are most useful when you're building new screens or reworking existing ones.

Create the Implementation Plan

/serious-plan

This is where your idea becomes a step-by-step action plan. Claude takes your research (or description) and generates a detailed plan: what to build, in what order, what tests to write, and how to verify each piece works. The plan is reviewed by AI personas before you see it.

When to use it

  • You know what to build and want a roadmap
  • After research, to turn findings into action
  • Before coding, so nothing gets missed
  • To coordinate multi-part changes

What you get

  • A detailed implementation_plan.md
  • Numbered tasks with acceptance criteria
  • Test-first (TDD) instructions per task
  • Risk levels and rollback plans
How to use it
What you type
> /serious-plan
 
Found completed research at
Research/bugs/random-logout/research.md
Use this as the basis for the plan?
1

Claude finds your research (or asks for input)

If you did /serious-research, Claude finds it automatically. Otherwise, you can point it to a document or just describe what you want to build.

2

Claude generates the plan

It breaks the work into numbered tasks (usually 3-7), each with specific acceptance criteria — clear checkboxes that define "done." Each task includes which files to change and what tests to write.

3

AI personas review the plan

A Senior Engineer checks for technical gaps. An Integration Architect checks for conflicts. Issues are fixed automatically — you see the final, reviewed version.

4

You approve the plan

Review it, ask questions, request changes. Once you're happy, the plan is ready for /serious-code to execute.

What a plan looks like (simplified)

Task 0: Smoke test — reproduce the logout bug in the running app.

Task 1: Fix token refresh logic in auth/token.js. Acceptance: token refreshes 5 min before expiry.

Task 2: Add retry logic for failed refresh attempts. Acceptance: 3 retries with backoff.

Task 3: Final smoke test — user stays logged in for 2+ hours.

⚠️
Big projects get split. If the work is large (8+ tasks or spans multiple areas), Claude will propose splitting it into multiple smaller plans that can run in parallel. This is normal and good.

Execute the Plan

/serious-code

This is where the code actually gets written. Claude reads your plan and works through each task in order: writes a failing test first, writes the code to make it pass, then verifies everything works. Five separate AI agents check each task independently. Nothing gets marked "done" unless all checks pass.

When to use it

  • You have an approved plan from /serious-plan
  • You want code written and verified automatically
  • You want evidence that each task actually works

What you get

  • Working code committed to your project
  • Tests for every acceptance criterion
  • Evidence reports proving each task works
  • A completion report summarizing everything
How to use it
What you type
> /serious-code
 
Found plan at Research/bugs/random-logout/implementation_plan.md
3 tasks, 1 high-risk. Execute?
1

Claude finds your plan and shows a summary

You'll see how many tasks, their risk levels, and what's about to happen. Say "Go" to start.

2

For each task, Claude runs the full cycle

Smoke test → see the current behavior
Stub check → catch placeholder code
Write failing test → define what "working" means
Write code → make the test pass
Verify → 5 AI agents check independently
Smoke test again → confirm it works in the actual app

3

If anything fails, it stops and tells you

Claude won't silently skip a failed task. It stops, explains what went wrong, and asks how you want to proceed: fix it, skip it, or roll back.

4

You get a completion report

When all tasks pass, Claude generates a report: what was built, what tests were written, all verification results, and evidence for each task.

What the evidence looks like

evidence/
  task_01/
    implementation.md ← what was changed
    review.md ← code review results
    tests.md ← test output
    runtime.md ← does it work in the app?
    qa.md ← spot-check results
    gate_passed.md ← proof it's done
  task_02/
    ...
completion_report.md
💡
You can walk away. Once you say "Go", Claude works through the tasks on its own. Come back and check the progress in the execution log. If something needs your input, it'll wait for you.

Review What Was Built

/serious-review

After code is written, review it. This skill does a structured review of the work, captures any defects, and if something needs fixing, it creates a new research/plan/code cycle to address it. Think of it as quality control that feeds problems back into the pipeline.

When to use it

  • After /serious-code finishes
  • When you want a second opinion on recent changes
  • To capture defects and cycle them back through the pipeline

What you get

  • Structured review of all changes
  • Defect list with severity
  • Automatic cycle-back for fixes
How to use it
What you type
> /serious-review
1

Claude reviews the recent work

It looks at what was built, checks it against the plan, and identifies any issues — missing edge cases, inconsistencies, potential bugs.

2

Defects get captured and categorized

Each issue gets a severity (critical, major, minor) and a description. You decide which ones to fix.

3

Fixes cycle back through the pipeline

If something needs fixing, it becomes a mini research → plan → code cycle (a "sub-workflow"). Your main work stays intact.

Utility Skills

The supporting cast

These aren't part of the main pipeline, but you'll use them regularly.

/serious-init

Set up a new project with Serious Sidekick. Run this once per project. It copies all the skills, hooks, templates, and documentation into your project folder.

> /serious-init

/serious-status

See all your active and completed workflows in a tree view. Shows what's in progress, what's done, and what was abandoned. Great for when you lose track of where you are.

> /serious-status

/serious-abandon

Hit a dead end? This cleanly exits the current workflow and returns you to the parent. Nothing is deleted — your work stays for reference, it's just marked "abandoned."

> /serious-abandon

/serious-bananas

Generate images and diagrams using Google's Gemini AI. Claude asks you 6 questions (what, type, style, ratio, variations, save location) then generates the image. Requires a Gemini API key in your .env file.

> /serious-bananas
Tips & FAQ

Things worth knowing

?

Do I have to use them in order?

No. Each skill works on its own. If you already know what to build, start at /serious-plan. If you already have a plan, start at /serious-code. The pipeline is a suggestion, not a requirement.

?

What if I need to go back a step?

That's what sub-workflows are for. If you're in /serious-plan and realize you need more research, just type /serious-research. Claude will ask if you want to link it as a sub-workflow. When the research is done, you pick up planning where you left off.

?

Where does everything get saved?

All output goes in a Research/ folder inside your project, organized by type: Research/bugs/, Research/features/, Research/exploratory/, or Research/conversations/. Everything is plain Markdown files — you can read them in any text editor.

?

Can I use this on any project?

Yes. Run /serious-init in any project folder. It works with any programming language and any framework. The skills don't write language-specific code themselves — they guide Claude, which adapts to your stack.

?

What if something goes wrong during /serious-code?

Claude stops at the failed task and asks you what to do. Your options: fix the issue and resume, skip the task, roll back the changes, or abort everything. Nothing is silently skipped. You can also use /serious-code --resume to pick up where it left off in a new session.

?

How is this different from just asking Claude to code?

When you just ask Claude to code, it writes something, says "done", and moves on. There's no verification, no evidence, no plan. Serious Sidekick adds structure: research before building, plans reviewed by personas, code verified by 5 independent agents, evidence that proves each piece works. It's the difference between "I think it works" and "here's proof it works."

💡
First time? Try this: open Claude Code in any project, type /serious-research, and describe something you've been curious about in your codebase. See what you learn. That's the best way to get started.
